## 4. Requirement traceability

For each requirement, cite the document number, edition and explicit clause. Keep the source of the project value separate from the source of the acceptance criterion. Do not use a supporting technical note to override a current standard.

Check superseded editions, draft status and amendments before assigning a conclusion. A proposed future value should not be presented as a requirement already in force.

## 5. Actions and evidence

State an action where a demonstrated issue requires one. For a compliant input, avoid creating a corrective action merely to fill the final column. Distinguish an optional future provision from work needed to meet a current requirement.

If evidence does not establish an answer, say so plainly rather than filling the table with an assumed value. Do not create additional project defects from the limited scope of the supplied extracts.

## 6. Review handover

Keep the completed table concise enough to review row by row. The reviewer should be able to open each cited clause and compare the stated requirement with the project value. Proposed changes should remain labelled as proposals until the design record is revised.
